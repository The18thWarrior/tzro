# tzro Agentic Dashboard

An agent-composed observability dashboard for the tzro execution engine. The dashboard layout is dynamically generated by the Local Model via a DAG pipeline, expressed as a JSON spec, translated to OpenUI Lang, and rendered by a React primitive library. Live data panels (event feed, notifications) stream independently via SSE.

## Overview

Unlike a traditional hardcoded dashboard, the tzro dashboard is a **Generative UI surface** where the agent controls what you see. A scheduled DAG task (default: every 4 hours) uses the Local Model to analyze current system state — task success/failure rates, active workflows, sidecar health, recent errors — and composes a dashboard layout from a fixed set of UI primitives. The agent decides ordering, emphasis, panel visibility, and can spotlight specific tasks or workflows that deserve attention.

The dashboard is a **first-class feature** of tzro, not an example app. It is served by the same Go HTTP process (tzrod/tzro-mcp) and exposed via MCP tools.

## Architecture

### Three-Layer System

```
┌────────────────────────────────────────────────────────────────┐
│ Layer 1: Dashboard Generation Pipeline (Go backend)            │
│                                                                │
│  Scheduled DAG (every 4h, or on-demand via MCP tool):          │
│                                                                │
│  [gather_metrics]  [gather_tasks]  [gather_config]             │
│        │                │               │                      │
│        └───────┬────────┘               │                      │
│                ▼                        │                       │
│      [gather_workflows]                 │                      │
│                │                        │                       │
│                └───────┬────────────────┘                      │
│                        ▼                                       │
│              [compose_layout]                                  │
│                        │                                       │
│                        ▼                                       │
│             [terminal_synthesis]                                │
│              → Writes JSON spec to SQLite                      │
└────────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────────┐
│ Layer 2: Dashboard API (Go server — new endpoints)             │
│                                                                │
│  GET  /api/dashboard/spec      → Latest cached JSON spec       │
│  POST /api/dashboard/regenerate → Trigger immediate regen DAG  │
│  GET  /dashboard               → Serve static frontend assets  │
└────────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────────┐
│ Layer 3: Frontend Renderer (React + OpenUI)                    │
│                                                                │
│  Fetch JSON spec → JSON→OpenUI Lang Adapter → <Renderer />    │
│                                                                │
│  Primitives:                                                   │
│    Static: MetricCard, ConfigPanel, Annotation,                │
│            TaskSpotlight, WorkflowSpotlight                    │
│    Live:   EventFeed (SSE), NotificationList (SSE),            │
│            TaskTable (polling), WorkflowMonitor (polling),     │
│            SidecarStatus (polling)                             │
│    Layout: Stack, Grid, Section                                │
│    Sub:    StatusBadge, DAGView                                │
└────────────────────────────────────────────────────────────────┘
```

### Key Architectural Decisions

- **JSON spec, not raw OpenUI Lang**: The Local Model generates a JSON dashboard spec under GBNF grammar constraints (guaranteed valid). A frontend adapter translates JSON → OpenUI Lang for the `<Renderer />`. This avoids forcing the 4B model to produce DSL syntax directly.
- **Hybrid static + live**: The spec controls placement and visibility of all primitives. Static primitives (MetricCard, Annotation) bake data into props at generation time. Live primitives (EventFeed, TaskTable) connect to SSE/polling independently — the spec only configures them (filters, limits).
- **Full agent control**: The agent decides the complete layout tree — panel ordering, grid arrangement, which metrics to surface, whether to spotlight a specific task. No hardcoded layout in the frontend.
- **Dashboard generates itself**: The generation pipeline uses the same execution engine (Kahn Compiler, GBNF constraints, compaction) that the dashboard monitors. The generation task itself appears in the task history.

## Component Primitive Library

15 primitives organized by behavior:

### Data Primitives (Static — props baked at generation time)

| Primitive | Props | Description |
|---|---|---|
| `MetricCard` | `label: string, value: string, trend?: "up" \| "down" \| "stable", trendValue?: string` | Single stat card with optional trend indicator |
| `ConfigPanel` | `entries?: Record<string, string>` | Key-value display of engine settings (read-only). If no entries provided, fetches live from `/api/config` |
| `Annotation` | `severity: "info" \| "warning" \| "error", text: string` | Agent-injected contextual insight card |
| `TaskSpotlight` | `taskId: string, showDAG?: boolean, showOutputs?: boolean` | Detailed single-task view with DAG visualization, node statuses, timing |
| `WorkflowSpotlight` | `workflowId: string, executionId?: string` | Detailed single-workflow view with execution timeline |

### Data Primitives (Live — self-refreshing)

| Primitive | Props | Data Source | Refresh |
|---|---|---|---|
| `TaskTable` | `limit?: number, filter?: "all" \| "running" \| "completed" \| "failed"` | `/api/tasks` | Polling (10s) |
| `EventFeed` | `maxItems?: number, typeFilter?: string[]` | `/api/events` | SSE (real-time) |
| `NotificationList` | `typeFilter?: ("warning" \| "error" \| "info" \| "action_required")[]` | `/api/notifications` | SSE + polling |
| `WorkflowMonitor` | `limit?: number` | `/api/workflows` + `/api/workflows/executions` | Polling (15s) |
| `SidecarStatus` | `{}` | `/api/sidecar` + `/api/models` | Polling (5s) |

### Layout Primitives

| Primitive | Props | Description |
|---|---|---|
| `Stack` | `children: Component[], gap?: "sm" \| "md" \| "lg"` | Vertical layout container |
| `Grid` | `children: Component[], columns: number, gap?: "sm" \| "md" \| "lg"` | CSS grid layout container |
| `Section` | `children: Component[], title: string, collapsible?: boolean` | Titled panel with optional collapse |

### Sub-Components (used within other primitives, not directly in spec)

| Primitive | Description |
|---|---|
| `StatusBadge` | Inline colored badge (completed, running, failed, pending) |

## JSON Dashboard Spec Schema

The Local Model generates this structure under GBNF constraints:

```json
{
  "version": 1,
  "generatedAt": 1749523200,
  "ttlSeconds": 14400,
  "layout": {
    "type": "Stack",
    "children": [
      {
        "type": "Grid",
        "columns": 3,
        "children": [
          {
            "type": "MetricCard",
            "props": {
              "label": "Total Tasks (24h)",
              "value": "42",
              "trend": "up",
              "trendValue": "+12%"
            }
          },
          {
            "type": "MetricCard",
            "props": {
              "label": "Success Rate",
              "value": "94%",
              "trend": "stable"
            }
          },
          {
            "type": "SidecarStatus",
            "props": {}
          }
        ]
      },
      {
        "type": "Annotation",
        "props": {
          "severity": "error",
          "text": "Task task_1749520800 failed. web_search node timed out after 3 retries."
        }
      },
      {
        "type": "TaskSpotlight",
        "props": {
          "taskId": "task_1749520800",
          "showDAG": true,
          "showOutputs": true
        }
      },
      {
        "type": "Grid",
        "columns": 2,
        "children": [
          {
            "type": "Section",
            "props": { "title": "Recent Tasks", "collapsible": true },
            "children": [
              { "type": "TaskTable", "props": { "limit": 10, "filter": "all" } }
            ]
          },
          {
            "type": "Section",
            "props": { "title": "Live Events" },
            "children": [
              { "type": "EventFeed", "props": { "maxItems": 50 } }
            ]
          }
        ]
      },
      {
        "type": "Section",
        "props": { "title": "Workflow Monitor", "collapsible": true },
        "children": [
          { "type": "WorkflowMonitor", "props": {} }
        ]
      },
      {
        "type": "Grid",
        "columns": 2,
        "children": [
          {
            "type": "Section",
            "props": { "title": "Notifications" },
            "children": [
              { "type": "NotificationList", "props": {} }
            ]
          },
          {
            "type": "Section",
            "props": { "title": "Engine Configuration" },
            "children": [
              { "type": "ConfigPanel", "props": {} }
            ]
          }
        ]
      }
    ]
  }
}
```

### Spec Constraints

- **`type`** is always a string matching a registered primitive name (GBNF enum constraint)
- **`props`** is a flat object per component, validated by the Zod schema on the frontend
- **`children`** is only present on layout primitives (Stack, Grid, Section)
- **Max nesting depth: 3** — `Stack` → `Grid` → `Section` → leaf primitive
- **Max primitives per spec: 30** — prevents runaway generation

## Dashboard Generation DAG

### Node Descriptions

| Node | Type | Description | Output |
|---|---|---|---|
| `gather_metrics` | Deterministic (Go) | Queries SQLite for task counts, success/failure rates, timing stats over 24h window. Pure database aggregation — no LLM. | `[{label, value, trend, trendValue}, ...]` |
| `gather_tasks` | Deterministic (Go) | Gets recent tasks, identifies failures and anomalies by rule (e.g. >2 failures/hour). Selects spotlight candidates by heuristic (most recent failure, longest-running task). | `{recentTasks: [...], spotlightCandidates: [...], failureCount: N}` |
| `gather_config` | Deterministic (Go) | Reads current engine config, sidecar status, active model. Snapshot of runtime state. | `{modelMode, cloudProvider, sidecarStatus, activeModel, ...}` |
| `gather_workflows` | Deterministic (Go) | Gets active workflows, recent executions. Selects spotlight candidates by heuristic (most active, recently failed). | `{workflows: [...], spotlightCandidates: [...]}` |
| `compose_layout` | LLM (Local Model) | Receives all gather fragments as context. The Local Model decides layout arrangement, ordering, emphasis, and which spotlight candidates to surface. Output constrained by GBNF grammar matching the dashboard JSON spec schema. | The complete JSON dashboard spec |
| `terminal_synthesis` | Deterministic (Go) | Validates the spec against the Zod-equivalent schema, writes to `dashboard_specs` table, prunes old specs (keep max 10). | `{specId, primitivesUsed, generatedAt}` |

### Dependencies

```
gather_metrics ──┐
gather_tasks ────┤
gather_config ───┼──→ compose_layout ──→ terminal_synthesis
gather_workflows ┘
```

The four `gather_*` nodes run in parallel. `compose_layout` waits for all four, then the Local Model produces the spec. `terminal_synthesis` validates and persists.

### GBNF Grammar for `compose_layout`

The GBNF grammar constrains the Local Model to produce only valid dashboard specs:

- `type` field restricted to enum: `"MetricCard" | "TaskTable" | "EventFeed" | "ConfigPanel" | "SidecarStatus" | "NotificationList" | "WorkflowMonitor" | "TaskSpotlight" | "WorkflowSpotlight" | "Annotation" | "Stack" | "Grid" | "Section"`
- `props` field constrained per component type
- `children` array only allowed on layout types
- Max depth enforced by grammar structure (no recursive rules beyond depth 3)

## MCP Tool Surface

### `tzro_dashboard`

Primary tool — ensures the HTTP server is running and returns the dashboard URL.

```
Args:
  port?: number          // Optional port override

Response:
  url: string            // e.g. "http://localhost:8090/dashboard"
  specAge: number        // Seconds since last spec generation
  nextRegeneration: number // Seconds until next scheduled regen
  status: "ready" | "generating" | "no_spec"
```

If no spec exists yet (first run), triggers an initial generation and returns `status: "generating"`.

### `tzro_dashboard_regenerate`

Force an immediate dashboard generation DAG. Follows the sync-with-timeout-fallback pattern from `tzro_run`.

```
Args:
  wait?: boolean         // Block until generation completes (default true)

Response (completed):
  status: "completed"
  generatorTaskId: string
  specVersion: string
  primitivesUsed: string[]
  generatedAt: number

Response (timed out):
  status: "generating"
  generatorTaskId: string
  message: string
```

### `tzro_dashboard_spec`

Read-only inspection of the current cached spec.

```
Args: (none)

Response:
  spec: object           // The full JSON dashboard spec
  generatedAt: number
  generatorTaskId: string
```

## Database Schema

New table in `tzro.db`:

```sql
CREATE TABLE IF NOT EXISTS dashboard_specs (
    id TEXT PRIMARY KEY,
    spec TEXT NOT NULL,
    generated_at INTEGER NOT NULL,
    generator_task_id TEXT,
    ttl_seconds INTEGER NOT NULL DEFAULT 14400
);
```

Only the latest spec is actively used. Historical specs are kept for debugging (capped at 10 rows with oldest auto-pruned on insert).

## Build & Serving

- **Build tool**: Vite with `@vitejs/plugin-react` and `@tailwindcss/vite` (matching existing web example setup)
- **Build output**: `vite.config.ts` targets `outDir` pointing to a `static/dashboard/` subdirectory within the Go project
- **Serving**: The Go HTTP server serves dashboard assets at `/dashboard` via `http.FileServer`
- **Dependencies**: `react`, `react-dom`, `@openuidev/react-lang`, `zod`, `lucide-react`

## Scheduling

- The dashboard generation DAG is registered as a system workflow with trigger type `cron` and a default interval of 4 hours
- On first `tzro_dashboard` MCP call, if no spec exists, an initial generation is triggered immediately
- `tzro_dashboard_regenerate` bypasses the schedule and triggers immediate generation
- The TTL field in the spec allows the frontend to show a staleness indicator ("Last generated: 2h ago")
